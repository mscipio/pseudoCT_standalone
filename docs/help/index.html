Overview

PseudoCT generates a subject-specific attenuation map from a T1-weighted MPRAGE using the SPM8-based atlas method described by Izquierdo-Garcia et al. It is intended for PET/MR workflows at the Athinoula A. Martinos Center for Biomedical Imaging.

Version and verification status

This page describes pseudoCT 3.3.0 as documented in the repository. Version 3.3.0 has not yet been published. This page is not a release, deployment or certification statement.

A compiled R2010b local run is reported as verified by the maintainer against v3.0.2. No evidence file for that run is included in the repository.

The MLSC submission path is implemented and tested offline. It has not been independently verified against a live scheduler.

Before processing

Choose the profile that matches the inputs and the output you need, click Run, keep MATLAB open until the run finishes, and review the QC image before using the generated map.

D. Izquierdo-Garcia, A.E. Hansen, S. Förster, D. Benoit, S. Schachoff, S. Fürst, K.T. Chen, D.B. Chonde, and C. Catana. An SPM8-based Approach for Attenuation Correction Combining Segmentation and Non-rigid Template Formation: Application to Simultaneous PET/MR Brain Imaging. Journal of Nuclear Medicine. 2014;55(11):1825–1830.

When using the method, cite the publication, and acknowledge the software and its maintainers as appropriate. See Scientific notes.

Requirements and distribution

An installed release runs on its own MATLAB Runtime. The default release, R2010b, runs on MATLAB Runtime 7.14. The other releases (R2014a to R2026a) are listed in the release catalog. A source checkout is for development only.

Quick start

  1. Load the installed application. 
    addpath('/usr/pubsw/packages/mrpet/standalone_apps/PseudoCT/pseudoCT_standalone-latest')
run_pseudo_CT

    A profile selector opens first. Choose one of the four profiles.

  2. Choose how to give the subjects. The window has two sources; only the selected one is used, and the two are never merged. One subject or many are handled the same way.
    • Enter subjects manually: click Add subject for each subject. Each subject has an ID (pre-filled, editable), an MPRAGE and, for the standard profiles, a UMAP. Use File... to choose a NIfTI or DICOM file, or Folder... to choose the folder that holds one DICOM series. You can also type or paste a path. Remove subject removes the selected subject. Export subjects file... saves the list as a subjects file you can reuse.
    • Load a subjects file: choose an existing subjects file (format in the reference). It is checked at once. The list shows the paths as written in the file, and the box below shows the file or DICOM series each path resolves to, or every error found. The file is read-only in the window; edit it in a text editor and press Check again.
  3. Check the UMAP references (standard profiles only). When you set an MPRAGE and the subject's UMAP is still empty, the window looks for a matching UMAP beside the MPRAGE and suggests it (marked (suggested) in the list). It never replaces a UMAP you chose. If none is found, select the UMAP yourself. MPRAGE-only profiles do not use a UMAP.
  4. Check the processing options. The defaults come from the profile.
  5. Click Run. Run first checks the whole subject list (paths and DICOM series; Check subjects does the same without running) and lists every error if it is not valid. It then validates the profile, the inputs, the outputs and the dependencies. Validation does not log in, contact remote services or run processing. Subjects are processed one after another.
    • Local profiles: Run submits the request as soon as validation passes.
    • MLSC profiles: Run validates first. Only after validation passes does a login dialog ask for your username, your password and an optional group account. Then the job is submitted once.
    • If validation fails, or you cancel the login dialog, nothing is submitted.
  6. Wait for the run to finish. The window stays open, but MATLAB is busy while Run runs. The inputs, the options and Close are disabled, and the window close button is ignored. Do not close MATLAB during an MLSC run.
  7. Read the result. A message box reports the outcome. A failure shows a warning with the error code. The status line at the bottom of the window also shows the outcome.
  8. Review the outputs and QC. Do not infer scientific completion from job submission or a scheduler state alone.

Requirements and installation details are in the Installation guide.

Choosing a profile

The window shows the profile names. The command line uses exactly these canonical keys:

Profile keyWhere it runsInputsOutputCluster login
localThis computerMPRAGE and UMAPNIfTI attenuation map, QC image, version record and DICOMNo
mlscMLSC cluster (Slurm), monitored from this computerMPRAGE and UMAPNIfTI attenuation map, QC image, version record and DICOMYes: MLSC username and password, optional group account
local-mprage-onlyThis computerMPRAGE onlyNIfTI attenuation map, QC image and version record; no DICOMNo
mlsc-mprage-onlyMLSC cluster (Slurm), monitored from this computerMPRAGE onlyNIfTI attenuation map, QC image and version record; no DICOMYes

The local and MLSC profiles run the same compiled pipeline. The profile chooses where it runs and which outputs are written, not a different algorithm. If the MLSC artifacts that a run requires are missing or invalid, the run stops before submission.

Each profile has its own defaults: nose and back aliasing correction on, recentering before normalization on, and removal of intermediate files after success on. You can change these in the window or on the command line (see Command line).

Command line

bin/pseudoct validate checks a request and is optional. bin/pseudoct run validates the same request and then submits it; it does not need a prior validate. Only --check-account logs in during validation.

bin/pseudoct validate --profile local \
  --mprage /subject/MR/MPRAGE/one.dcm \
  --umap /subject/MR/UMAP/one.dcm
bin/pseudoct run --profile local \
  --mprage /subject/MR/MPRAGE/one.dcm \
  --umap /subject/MR/UMAP/one.dcm
  • --profile NAME (required): one of the four canonical profile keys.
  • --mprage FILE [--umap FILE]: one subject. On standard profiles the UMAP may be omitted, and the command line then tries to find it in the subject layout. MPRAGE-only profiles reject --umap.
  • --config job.json: several subjects. The JSON object has a non-empty mprage array and an optional umap array, paired by position: 
    {"mprage":["/data/one/MPRAGE.dcm","/data/two/MPRAGE.dcm"],
 "umap":["/data/one/UMAP.dcm","/data/two/UMAP.dcm"]}
  • --correct-aliasing yes|no, --recenter-before-normalization yes|no, --cleanup-on-success yes|no: change the profile defaults.
  • --group-account ACCOUNT (MLSC): the cluster account. If it is omitted, the first account found for you is used.
  • --check-account (MLSC, validate only): logs in, checks the account and stops. It never submits.
  • --format text|jsonl: text (default) prints readable progress. jsonl prints one JSON record per line, for scripts.
  • --result-file PATH: also writes the final result record to PATH, in either format.
  • bin/pseudoct --help prints the usage text of the installed launcher.

Passwords are never accepted on the command line. For MLSC, the command line asks for the username and the password at the terminal, and the password is not shown as you type it.

Preparing input data

Standard profiles

MPRAGE + UMAP

Provide an MPRAGE (DICOM or NIfTI) and its matched UMAP reference. The window looks for the UMAP in the subject's MR folder: it searches for a sub-folder whose name contains umap, ute, mu_map or mumap, and uses the first file in that folder whose name contains 0001. The suggestion is made only while the subject's UMAP is empty. If nothing is found, select the UMAP yourself. An MPRAGE or UMAP can also be a folder that holds exactly one DICOM series. Confirm the selected inputs before you click Run.

MPRAGE-only profiles

MPRAGE only

Provide an MPRAGE without a UMAP. These profiles reject a UMAP and write NIfTI output only.

The examples use the subject layout <subject>/MR/MPRAGE/ and <subject>/MR/UMAP/. For multi-subject requests on the command line, pair the MPRAGE and UMAP entries by position (see Command line).

MLSC login and submission

For the MLSC profiles, Run validates the inputs without logging in. If validation passes, a login dialog asks for your MLSC username, your password and an optional group account. Then the job is submitted to Slurm, monitored, and its outputs are copied back and finalized locally. The password is used for the login only. It is not written to any file.

  • Use an MLSC profile and an account that is authorized for the project.
  • Make sure the configured shared filesystem, the subject folder and the inputs are reachable from the cluster.
  • Cancelling the login dialog submits nothing.
  • If the login is rejected, the window reports the failure and the login dialog reopens automatically. Enter the password (and the account) again. Cancel submits nothing. Nothing is submitted without a successful login.
  • Keep MATLAB open until monitoring and output finalization finish.
  • Do not treat an accepted submission or a Slurm COMPLETED state alone as a verified pseudoCT result. The result is verified only when the required outputs and their copy-back evidence are verified.

MLSC submission is implemented and tested offline. It has not been independently verified against a live scheduler or cluster.

Outputs

Final outputs

Written under the subject's MR_PET/ folder.

Attenuation map

The NIfTI attenuation map is att_map.nii. All four profiles write it.

QC and version

The QC image is Fusion_MR_Pseudo_CT_validation.tiff. The version record is Pseudo_CT_AC_Version.txt.

DICOM

Standard profiles write DICOM under MR/pseudo_muMAP/. MPRAGE-only profiles produce no DICOM.

Inspect the QC image for every subject before you use the map (see Quality control).

Temporary files

Working files for each subject are in MR_PET/tmp/. They are removed after a successful run when cleanup on success is on. They are kept when a run fails or cleanup is off.

Files written by a run

Every run writes two files per subject, in the subject's MR_PET/ folder. Both share the same name stem, pseudoct-run-<UTC>-<invocation>. <UTC> is the start time, and <invocation> identifies the run.

FileWhat it containsUse
pseudoct-run-<UTC>-<invocation>.jsonlOne JSON record per line: stage records (status per stage), run records (outcome: succeeded, failed or cancelled), and warning, error and lifecycle records. It is written at the phase boundaries and kept after success, failure and cancellation. Heartbeats are not written to it.The canonical machine-readable record of the run. Use it for records and scripts.
pseudoct-run-<UTC>-<invocation>.logThe detailed run log, including heartbeat lines and the raw diagnostics of the processing steps. It is not a copy of the console table. It is created after validation and output-location resolution, and it is not deleted by the application.Detailed diagnosis. Keep it for support.

validate writes one file instead: pseudoct-validate-<UTC>-<invocation>.jsonl, with one result record, in the subject's MR_PET/ folder. It is written only when that folder can be found. If it cannot be found, the message on stderr says that no validation record was written. Validation creates no run log.

No passwords or login details

Passwords and login details are never written to either file or to the validation record.

Progress and exit codes

  • Text (command line default): progress is printed to the terminal, one row per stage and event. [n/10] is the stage number. SKIPPED shows a stage that does not apply to the profile, with its reason. Stages 2 and 3 show ACTIVE only once the operation has run, and SKIPPED with a reason otherwise. For MPRAGE-only profiles, stages 9 and 10 are SKIPPED by policy, because no DICOM output is written and the output is not finalized as a full run.
  • Warnings and errors are shown as WARN and ERROR rows during the run. A still running line shows that a long step is in progress.
  • JSONL (--format jsonl): one JSON record per line. The final record carries the outcome and the exit code, the submission and scientific-completion fields and, for MLSC, the job IDs. It does not carry run-log paths: these are printed in the text summary. Each run's files carry the same invocation ID as the result record.
  • Completion is reported when the scientific processing is complete and verified. Only then is the exit code 0.
  • In the window, the progress text is sent to the MATLAB Command Window. Whether it appears live during the run has not yet been confirmed on the installed MATLAB. The files in Files written by a run are the complete record either way.

Cancellation

  • Before submission: the cluster has accepted nothing, so there is nothing to cancel. Cancelling the MLSC login dialog stops before submission.
  • Timeout: if the monitoring reaches its configured timeout before the job's final state is known, the launcher asks the scheduler to cancel the job and then reports the outcome. If the final state is still unavailable, the result is a timeout failure, not a completion.
  • Interruption after submission: an error while monitoring, a lost connection or Ctrl-C after the Slurm job was accepted does not cancel the job. The result is reported as unverified (exit 68 on the command line). The job ID and the command scancel <job id> are printed. The job keeps running until you cancel it by hand.
  • Window: there is no cancel button for a running request. Close and the window close button do not stop it. The window stays busy until the run finishes.

Quality control

Review QC for every subject before using an attenuation map in PET processing.

  • Inspect the MPRAGE and pseudoCT fusion QC image for registration and anatomical coverage.
  • Scroll through the final volume and check for misregistration, missing anatomy or unexpected attenuation outside the head.
  • Confirm that the outputs belong to the intended subject and that completion was verified.
  • The run log and the JSONL file record what happened. They do not replace the QC review.
  • Document any failure or questionable result. Do not assume that one successful subject establishes general accuracy; see Scientific notes.

Troubleshooting

SymptomWhat to do
Login failed (authentication failed, exit 66) In the window, the login dialog reopens automatically: enter the password (and the account) again, or press Cancel to submit nothing. On the command line, you are asked again for the password (and for the account, if you did not give --group-account). An empty input cancels the retry. Retries are unlimited unless the administrator sets PSEUDOCT_AUTH_RETRY_LIMIT. With a limit of N, the run stops after N retries, with exit 66 and nothing submitted. The limit applies only to the command-line prompt.
Invalid group account Enter a valid account. On the command line with --group-account, the run stops with exit 66. Run it again with a valid account.
Host key problem (HOST_KEY_UNAVAILABLE) Not retried: the run stops with exit 66. Contact the application maintainer.
Input not found Check the MPRAGE or UMAP path, the subject folder and that the file can be read.
Reference missing Select the matched UMAP yourself, or choose an MPRAGE-only profile if that is appropriate. MPRAGE-only profiles reject a UMAP.
Run is disabled Check that the MPRAGE (and, for standard profiles, the UMAP) can be read. Run is also disabled while a request is running.
"This is a source checkout" message The window was started from a source checkout, which is for development only. Use the installed application.
"Installation is incomplete" message Files of the installed application are missing (the runtimes folder). Reinstall the distribution.
MATLAB Runtime not found, or identity mismatch The runtime for the selected release is found from the release catalog. Do not substitute another runtime or resource path. Contact the maintainer if the runtime is installed elsewhere.
Dependency or artifact check failed Stop, and contact the application maintainer. Do not substitute a different runtime or resource path.
MLSC job still running Leave MATLAB open and let the monitoring finish. Do not submit a duplicate job.
Exit 68 after a submitted job The outcome is unverified. Keep the run log and the JSONL file. If the job must stop, cancel it by hand with scancel.
Outputs or QC incomplete Treat the run as unverified. Keep its log and JSONL file for support.
