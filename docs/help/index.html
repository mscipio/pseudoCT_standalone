Overview

PseudoCT generates a subject-specific attenuation map from a T1-weighted MPRAGE using the SPM8-based atlas method described by Izquierdo-Garcia et al. It is intended for PET/MR workflows at the Athinoula A. Martinos Center for Biomedical Imaging.

Version and verification status

This page describes pseudoCT 3.2.0 as documented in the repository. Version 3.2.0 is unpublished prerelease work. This page is not a release, deployment or certification statement.

A compiled R2010b local run is reported as verified by the maintainer against v3.0.2. No evidence file for that run is included in the repository.

The MLSC installed submit path is implemented and offline-tested. It has not been independently verified against a live scheduler.

Before processing

Choose the profile that matches the input/reference and output policy, Validate before you Submit, keep MATLAB open during a run, and review the QC before using the generated map.

D. Izquierdo-Garcia, A.E. Hansen, S. Förster, D. Benoit, S. Schachoff, S. Fürst, K.T. Chen, D.B. Chonde, and C. Catana. An SPM8-based Approach for Attenuation Correction Combining Segmentation and Non-rigid Template Formation: Application to Simultaneous PET/MR Brain Imaging. Journal of Nuclear Medicine. 2014;55(11):1825–1830.

When using the method, cite the publication, and acknowledge the software and its maintainers as appropriate. See Scientific notes.

Requirements and distribution

A source checkout needs R2010b-compatible MATLAB (MATLAB 7.11 minimum). An installed release runs on its own MATLAB Runtime (MCR). The default release, R2010b, runs on MATLAB Runtime 7.14. The other exact labels (R2014a to R2026a) are listed in the release catalog.

An installed distribution contains one command-line launcher (bin/pseudoct), one MATLAB entry point (run_pseudo_CT), and, for each release, two compiled executables: the job manager pseudoct_job_manager and the science pipeline pseudoct_pipeline. It does not ship build or resource manifests. See the distribution layout.

Quick start

  1. Load the deployed installation. 
    addpath('/usr/pubsw/packages/mrpet/standalone_apps/PseudoCT/pseudoCT_standalone-latest')
run_pseudo_CT
  2. Select one of the four supported profiles and choose Run Selected. The standard profiles use an MPRAGE and a UMAP reference; MPRAGE-only profiles do not use a UMAP.
  3. Select or confirm the input files. Use the file selectors and verify that the subject and reference belong together.
  4. Click Validate. Validate checks the profile, inputs, outputs and dependencies. It does not authenticate, contact remote services or run processing.
  5. Click Submit. Submit is enabled only after a successful Validate of exactly the current profile, input files and options. Changing any of them disables Submit until you Validate again. Each Submit uses up its validation.
  6. Wait for the request to finish. The window stays open, but MATLAB is busy while Validate or Submit runs. Close only closes the window; it does not stop a running request. For MLSC, keep MATLAB open until monitoring and output finalization finish.
  7. Review the outputs and QC. Do not infer scientific completion from job submission or a scheduler state alone.

Requirements and installation details are in the Installation guide.

The window shows display names. The command line, the MATLAB API and the launcher use exactly these canonical keys:

The local and MLSC profiles run the same shared compiled pipeline. The profile chooses the execution location and the input/output policy, not a different algorithm. Missing or invalid MLSC artifact requirements fail closed.

Profile defaults come from the profile files: nose/back aliasing correction on, recentering before normalization on, and cleanup of intermediate files after success on. The command line can override each of them (see Command line).

Command line

bin/pseudoct run validate checks a request. bin/pseudoct run run validates the same request and then submits it.

bin/pseudoct run validate --profile local \
  --mprage /subject/MR/MPRAGE/one.dcm \
  --umap /subject/MR/UMAP/one.dcm --format jsonl
bin/pseudoct run run --profile local \
  --mprage /subject/MR/MPRAGE/one.dcm \
  --umap /subject/MR/UMAP/one.dcm --format jsonl
  • --profile NAME (required): one of the four canonical keys.
  • --mprage FILE [--umap FILE]: one subject. The UMAP may be omitted on standard profiles. MPRAGE-only profiles reject --umap.
  • --config job.json: several subjects. The JSON object has a non-empty mprage array and an optional umap array, paired by position: 
    {"mprage":["/data/one/MPRAGE.dcm","/data/two/MPRAGE.dcm"],
 "umap":["/data/one/UMAP.dcm","/data/two/UMAP.dcm"]}
  • --correct-aliasing yes|no, --recenter-before-normalization yes|no, --cleanup-on-success yes|no: override the profile defaults.
  • --current-artifact-root PATH: development-only override, accepted only with the MLSC profiles; local profiles reject it.
  • --group-account ACCOUNT, --host-key-file FILE, --credential-handoff FILE: MLSC inputs. The handoff is an existing single-use credential file created for the submit step.
  • --format text|jsonl: output format (default text). bin/pseudoct --help prints the installed usage text.

Credentials are never accepted on the command line. MLSC submit authenticates with a terminal prompt or with the one-time --credential-handoff file.

Preparing input data

Standard profiles

MPRAGE + UMAP

Provide an MPRAGE (DICOM or NIfTI) and its matched UMAP reference. If the UMAP is omitted, the application may discover it from the subject layout. Confirm the selected files before submitting.

MPRAGE-only profiles

MPRAGE only

Provide an MPRAGE without a UMAP. These profiles reject a UMAP and write NIfTI-only output.

The examples use the subject layout <subject>/MR/MPRAGE/ and <subject>/MR/UMAP/. For multi-subject requests, pair the MPRAGE and UMAP entries by position (see Command line).

MLSC workflow

The MLSC profiles submit the job to Slurm after a successful Validate of the same inputs and options. Submit authenticates, submits the job, monitors it, and finalizes the local outputs. In the window, Submit asks for the login in a dialog and passes only a single-use credential handoff path to the launcher.

  • Use an MLSC profile and an account authorized for the project.
  • Make sure the configured shared filesystem, the subject workspace and the inputs are accessible from the cluster.
  • The default Slurm request for MLSC profiles is 1 node, 1 task, 4 CPUs, 8 GB memory and a 2-hour time limit.
  • Keep MATLAB open until monitoring and output verification finish.
  • Do not treat an accepted submission or Slurm COMPLETED alone as a verified pseudoCT result. Completion is verified only when the required outputs and copy-back evidence are verified.
Verification status

MLSC installed submit is implemented and offline-tested. It has not been independently verified against a live scheduler or cluster.

Never place passwords, private keys or other credential values in CLI arguments, environment variables, request files or logs.

Outputs

Final outputs

Written under the subject's MR_PET/ directory.

Attenuation map

The NIfTI attenuation map is att_map.nii. All four profiles write it.

QC and version

The QC image is Fusion_MR_Pseudo_CT_validation.tiff. The version record is Pseudo_CT_AC_Version.txt.

DICOM

Standard profiles write DICOM under MR/pseudo_muMAP/. MPRAGE-only profiles produce no DICOM.

Run log and events

  • Each subject gets one owner-only run log, MR_PET/pseudoct-run-<UTC>-<invocationUUID>.log. It is created after validation and output-location resolution. The pipeline never deletes or prunes it.
  • Scientific and MLSC lifecycle events are appended as JSONL to MR_PET/pseudoct-run-<UTC>-<invocationUUID>.jsonl. They are kept after success, failure and cancellation.

Temporary files

Per-subject working files are in MR_PET/tmp/. They are removed after a successful promotion when cleanup on success is on, and kept when promotion fails or cleanup is off. The command line's private invocation directory under MR_PET/tmp/ is removed when the launcher exits.

Progress, logs and exit codes

  • Text (default): progress is printed to the console.
  • JSONL (--format jsonl): one JSON record per line, for progress and for the final result. The result record carries the exit code and, for MLSC, the job IDs and run-log paths.
  • The window shows the launcher's result when a request finishes. MATLAB is busy while a request runs.

bin/pseudoct run validate and bin/pseudoct run run return:

CodeMeaning
0Validation passed, or the run completed with verified results.
64Usage or configuration error.
65Invalid request or validation failure.
66Authentication failure.
67Submission failure.
68Scientific failure, or completion not verified.
69Launcher or runtime failure.
70MATLAB dispatch or runtime failure (listed in --help): the MATLAB CLI support, diagnostics or headless bootstrap could not start or returned no valid result. See the CLI reference.

Cancellation

  • Before submission: the scheduler has accepted nothing, so there is nothing to cancel. Cancelling the MLSC login dialog stops before submission.
  • Timeout: if polling reaches the configured timeout before terminal accounting, the launcher requests cancellation with scancel and then reports the outcome from accounting. If terminal accounting is still unavailable, the result is a timeout failure, not a completion.
  • Interruption after submission: a polling error, a lost connection or Ctrl-C after the Slurm job was accepted does not cancel the job. The result is reported as unverified (exit 68 for bin/pseudoct run). The job ID and the command scancel <job id> are printed. The job keeps running until you cancel it by hand.
  • Window: there is no in-application cancel control. Close closes the window only and does not stop a running request; MATLAB stays busy while a synchronous request runs.

Quality control

Review QC for every subject before using an attenuation map in PET processing.

  • Inspect the MPRAGE/pseudoCT fusion QC image for registration and anatomical coverage.
  • Scroll through the final volume and check for misregistration, missing anatomy or unexpected attenuation outside the head.
  • Confirm that outputs belong to the intended subject and that completion was verified.
  • Run logs and JSONL events record what happened, but they do not replace the QC review.
  • Document any failure or questionable result. Do not assume that one successful subject establishes general accuracy; see Scientific notes.

Troubleshooting

  • Input not found: check the MPRAGE or UMAP path, the subject directory and file readability.
  • Reference missing: select the matched UMAP explicitly, or choose an MPRAGE-only profile if appropriate. MPRAGE-only profiles reject a UMAP.
  • Submit is disabled: Validate the current inputs and options again. Any change disables Submit.
  • MATLAB Runtime not found or identity mismatch: the MATLAB Runtime root is resolved automatically from the catalog convention for the selected release, and --mcr-root is an optional explicit override. No environment variable is read. The runtime identity is checked against the release catalog, and a root never bypasses that check.
  • Dependency or artifact validation failed: stop and contact the application maintainer. Do not substitute a different runtime or resource path.
  • MLSC still running: leave MATLAB open and let the existing monitor finish. Do not submit a duplicate job.
  • Exit 68 after a submitted job: the outcome is unverified. Keep the run log and JSONL events. If the job must stop, cancel it by hand with scancel.
  • QC or outputs incomplete: treat the run as unverified and retain its diagnostics for support.
