Overview

The Martinos pseudoCT package generates a subject-specific attenuation map from a T1-weighted MPRAGE image using the atlas-based method described by Izquierdo-Garcia et al.

It is intended for PET/MR attenuation-correction workflows at the Athinoula A. Martinos Center for Biomedical Imaging. MPRAGE input can be supplied either as the original DICOM series or as a preprocessed NIfTI image (.nii or .nii.gz).

Routine use

For normal subject processing, use the Local MATLAB (Current) profile.

Reference

D. Izquierdo-Garcia, A.E. Hansen, S. Förster, D. Benoit, S. Schachoff, S. Fürst, K.T. Chen, D.B. Chonde, and C. Catana. An SPM8-based Approach for Attenuation Correction Combining Segmentation and Non-rigid Template Formation: Application to Simultaneous PET/MR Brain Imaging. Journal of Nuclear Medicine. 2014;55(11):1825–1830.

Software location and versions

PseudoCT is deployed at:

/usr/pubsw/packages/mrpet/standalone_apps/PseudoCT/

Which version should I use?

For a new subject or a new study, users should normally use pseudoCT_standalone-latest.

Long-running studies: pin a numbered release

If processing for a study will take place over an extended period, select a specific numbered release and use the same version for the entire study. This maintains software-version consistency across the dataset.

New versions will be deployed regularly to add functionality or fix minor issues. If a problem is discovered that makes continued use of an older version inadvisable, that change will be explicitly communicated and motivated.

Quick start

  1. Add pseudoCT to the MATLAB path. 
    addpath('/usr/pubsw/packages/mrpet/standalone_apps/PseudoCT/pseudoCT_standalone-latest')
  2. Run pseudoCT. 
    run_pseudo_CT
  3. Select Local MATLAB (Current) for routine processing.
  4. Select the first DICOM of the MPRAGE series, or select the single preprocessed NIfTI file.
  5. Confirm that the UMAP has been found automatically.
  6. Leave the automatic MPRAGE correction options enabled unless you have a specific reason not to.
  7. Click OK and keep MATLAB open until the run finishes.
  8. Inspect both the TIFF fusion image and the final DICOM pseudoCT before using it for attenuation correction.

It is recommended to run pseudoCT from a working directory close to the data rather than changing into the software installation directory.

To pin processing to a numbered release, use that directory explicitly: 

addpath('/usr/pubsw/packages/mrpet/standalone_apps/PseudoCT/pseudoCT_standalone-<version>')

Execution profiles

Local MATLAB (Current)

Recommended

Runs the full MPRAGE + UMAP workflow locally on the workstation using the current Martinos MATLAB environment. This is the recommended profile for routine processing.

On an average workstation, expect approximately 30 minutes per subject.

mlsc (Recommended Remote/Cluster Workflow)

Recommended remote

MLSC is the replacement remote/cluster workflow for Launchpad. The standard MLSC profile runs the MPRAGE + UMAP workflow and requires the UMAP reference. It produces both NIfTI and DICOM output.

Expected processing time is approximately 1 hour per subject, excluding queue wait. MLSC is not production-ready until the live readiness checks described below have passed.

[Specialized] mlsc_mprage_only - MPRAGE Only

Not for routine use

This specialized MLSC profile processes an MPRAGE without requiring a UMAP reference and produces NIfTI output only. It is intended for known specialized workflows, not routine processing.

Launchpad (Aether Legacy Workflow)

Currently unavailable

This is the historical compiled backend. Launchpad is currently unavailable and will soon be discontinued/decommissioned. MLSC is its replacement remote/cluster workflow.

The Launchpad source and profile are retained only for transitional/reference purposes. Do not treat Launchpad as a recommended or usable remote workflow.

Specialized / Development profiles

Additional profiles exist for specific systems, validation work, compatibility testing, and development. The MLSC MPRAGE-only profile is documented here because its no-reference/NIfTI-only behavior is explicit; other specialized profiles are not intended for routine use.

If you do not already know why you need a specialized profile, do not select one.

MLSC / Slurm remote workflow

MLSC is the replacement remote/cluster workflow for Launchpad. It uses the existing compiled pseudoCT runner, Slurm, and the shared filesystem. The SSH connection is a control path only: MPRAGE files, scripts, and outputs are not staged over SCP or another network payload channel.

Production readiness is not claimed

MLSC remains not production-ready until the four live readiness checks below all pass: remote true returning exit status 0, sshare account discovery, a lightweight Slurm/$TMPDIR test, and a one-subject end-to-end run. Crypto/transport compatibility is already proven by a manual diagnostic that authenticated to MLSC through the bundled Ganymed library and returned the login hostname mlsc-login.nmr.mgh.harvard.edu.

Runtime login and Slurm account

MLSC uses the existing username/password SSH workflow, analogous to the historical Launchpad login: the same modal passwordEntryDialog-style username/password prompt at runtime, followed by password authentication through the bundled Ganymed SSH2 transport. No host-key setup is required for normal use. Credentials are entered at runtime, held transiently, cleared after use, and never persisted in profiles, commands, environment variables, scripts, logs, or evidence. Cancelling the login dialog submits no job, and a rejected password fails the connection without any account query or submission attempt.

After authentication, the authenticated user’s available accounts are discovered at runtime with sshare -U -u $USER. Zero accounts fails before submission. One account is selected automatically. Multiple accounts are shown in a single-selection dialog. Cancelling the dialog submits no job. The selected account is not saved as profile configuration or reused by a later run.

A strict pinned host-key verification mode exists only as an optional development/testing opt-in for maintainers. It is never required for normal processing and does not change the workflow described above.

Shared filesystem and node-local staging

MATLAB first writes each subject’s input to the shared subject temporary directory, normally <subject>/MR_PET/tmp/mprage.nii. A generated per-subject script then uses normal filesystem cp to copy the input into a writable, node-local $TMPDIR. The script rejects an empty, unavailable, unwritable, or shared $TMPDIR.

FreeSurfer mri_normalize and the unchanged compiled runner execute after changing directory to node-local $TMPDIR. FreeSurfer is sourced only inside the batch shell, and is invoked with env -u LD_LIBRARY_PATH so MATLAB/local runtime library paths do not leak into the FreeSurfer child process. The job sets OMP_NUM_THREADS and MKL_NUM_THREADS from $SLURM_CPUS_PER_TASK and uses the node-local $TMPDIR/mcr_cache for the MCR cache.

The current request is exactly: partition basic, 1 node, 1 task, 4 CPUs per task, 8G, and 2 hours. The expected runtime is approximately 1 hour per subject, excluding queue wait.

Submission, monitoring, and failure handling

The runtime account is passed only to a parsable submission such as: 

sbatch --parsable --account <runtime-account> -- <shared-script-path>

The lifecycle reads stable scheduler output with: 

squeue --noheader --jobs=JOBID --format=%T
sacct --allocations --noheader --parsable2 --jobs=JOBID \
  --format=JobIDRaw,State,ExitCode,Start,End,Elapsed

sacct primary-allocation state and exit code are authoritative for terminal results, including delayed accounting. Pending, running, completed, failed, cancelled, timeout, out-of-memory, node-failure, and unknown results are normalized. A bounded timeout requests cancellation and records an unresolved result as timeout or unknown rather than claiming success.

A non-empty node-local att_map.nii is required. It is copied with normal cp back to the shared subject temporary directory and verified non-empty there. Missing or empty output, non-zero exit status, failed copy-back, failed accounting, or any non-success scheduler result prevents local finalization.

Local finalization and cleanup

Only after verified copy-back does MLSC reuse the existing local post-remote finalization path. The standard profile optionally applies the local background mask, converts the NIfTI attenuation map to DICOM using the UMAP geometry, and promotes outputs with the same finalizer used by the Launchpad path. The MPRAGE-only profile skips DICOM by policy and promotes NIfTI output only.

att_map.nii is required. The QC fusion TIFF, version record, and normalized MPRAGE are optional outputs when produced; available files are copied back and promoted. Slurm removes node-local $TMPDIR when the job exits. Normal pseudoCT cleanup removes the shared MR_PET/tmp/ after successful promotion when enabled; failed or interrupted runs retain temporary files for inspection.

Logs and evidence

Each subject receives a local log under MR_PET named pseudo_CT_mlsc_<runid>.log, plus the usual pseudo_CT_profile_summary.txt. These record the selected profile, paths, stages, scheduler/failure details, and final status. The credential-free lifecycle evidence schema is pseudo-CT.mlsc-evidence/v1; when an evidence directory is configured it is written as mlsc_evidence.mat and records the account, job ID, timestamps, state/exit data, staging contract, copy-back, cleanup, and failure detail. Username, password, and SSH internals are rejected from evidence.

Ordered live readiness checks

  1. A) Remote true exit status. Using the normal login workflow above, run exactly true on MLSC and require a numeric SSH exit status of 0. A TCP connection, authentication success, or empty output alone is not sufficient.
  2. B) sshare account discovery. Confirm that sshare -U -u $USER returns the authenticated user's Slurm accounts and that the zero/one/multiple/cancel selection behavior works.
  3. C) Lightweight Slurm/$TMPDIR test. Submit a minimal job with the standard resource request and confirm that the batch shell receives a writable, node-local $TMPDIR, that sbatch --parsable returns one numeric job ID, and that the machine-readable squeue and sacct queries work.
  4. D) One-subject E2E. Verify node-local normalization and compiled-runner execution, required and optional outputs, non-empty shared copy-back, lifecycle logs/evidence, existing local finalization, DICOM output for standard mlsc, and cleanup of node-local $TMPDIR and normal shared temporary data.

MATLAB must remain open while the Slurm job is monitored and while local finalization is performed. Credential-free tests do not replace these live checks; production readiness is not claimed until checks A–D all pass.

See the detailed MLSC/Slurm pipeline documentation for the full staging contract, connection model, and output handling.

Preparing the input data

The standard PET/MR workflow requires a T1-weighted MPRAGE and a corresponding UMAP. PseudoCT supports either the original MPRAGE DICOM data or a preprocessed MPRAGE NIfTI.

DICOM MPRAGE

The minimum required folder structure is:

<subject>/
└── MR/
    ├── MPRAGE/
    └── UMAP/

When selecting the MPRAGE, choose the first DICOM file of the MPRAGE series. The MR_PET folder does not need to exist before processing; pseudoCT creates it.

Preprocessed NIfTI MPRAGE

If preprocessing is needed, place the resulting .nii or .nii.gz image in <subject>/MR_PET/. The original MR/MPRAGE and MR/UMAP folders may remain in place. 

<subject>/
├── MR/
│   ├── MPRAGE/
│   └── UMAP/
└── MR_PET/
    └── preprocessed_mprage.nii.gz
Why preprocess the MPRAGE?

In some subjects, noise in the image background can interfere with segmentation and can ultimately produce spurious tissue-like attenuation values outside the head. Background cleanup may be useful in those cases. A dedicated preprocessing tool is planned for release.

Single-subject workflow

After selecting Local MATLAB (Current), the Load Images dialog is shown.

1. Load the MPRAGE

Click Load MPRAGE. For DICOM input, select the first file in the MPRAGE series. For NIfTI input, select the single .nii or .nii.gz file.

2. Confirm the UMAP

When the expected directory structure is present, pseudoCT automatically searches the sibling MR/UMAP folder and populates the UMAP field. In normal use, you should not need to click Load UMAP manually.

3. MPRAGE correction options

PseudoCT can apply automatic preprocessing to improve segmentation and registration to the MNI atlas, including correction of nose/neck wrap-around aliasing and recentering of the brain within the field of view.

Recommended

Leave automatic aliasing correction and recentering enabled. The application determines whether a correction is actually required, so leaving these options ON is the preferred approach in most cases.

The preprocessing controls are currently being revised, so their exact appearance may change between releases.

4. Start processing

Once the input paths are correct, click OK. MATLAB must remain open for the duration of the run.

Batch processing

Multiple subjects can be selected in one run using the batch file picker: 

run_pseudo_CT('profile', 'local-current', 'subjects', 'batch')

Select the first MPRAGE DICOM for each subject (or the desired NIfTI input for each subject), then click Done. PseudoCT processes the selected subjects sequentially and discovers each subject's UMAP from the expected folder structure.

Study consistency still applies

For a long-running study, run the batch with the same numbered pseudoCT release used for the rest of the study rather than switching versions midway through processing.

During processing

Local execution takes approximately 30 minutes per subject on an average workstation. MLSC execution is expected to take approximately 1 hour per subject, excluding queue wait. The exact time depends on the workstation, cluster, and input data.

MATLAB prints stage-by-stage status messages and writes a detailed run log in MR_PET.

Interrupting a run

It is safe to interrupt pseudoCT, but interruption stops the current processing run. Intermediate files generated up to that point are retained.

Starting pseudoCT again for the same subject restarts processing from the beginning and overwrites existing processing files as needed.

Keep MATLAB running

Closing MATLAB or interrupting execution stops the local run. For MLSC, MATLAB must remain open while the Slurm job is monitored and while local finalization is performed.

Outputs

PseudoCT creates the required output directories automatically. After a successful Local MATLAB run, the subject directory contains: 

<subject>/
├── MR/
│   ├── MPRAGE/
│   ├── UMAP/
│   └── pseudo_muMAP/
│       └── final DICOM pseudoCT series
└── MR_PET/
    ├── att_map.nii
    ├── Fusion_MR_Pseudo_CT_validation.tiff
    ├── MPRAGE_spm.nii
    ├── MPRAGE_spm_normalized.nii
    ├── Pseudo_CT_AC_Version.txt
    ├── pseudo_CT_local-current_*.log
    └── pseudo_CT_profile_summary.txt

The standard mlsc profile uses the same final output layout after verified copy-back and local finalization. Its required output is MR_PET/att_map.nii; the QC fusion TIFF, version record, and normalized MPRAGE are optional when produced. The specialized mlsc_mprage_only profile does not require a UMAP and produces NIfTI output only, so it does not create the final DICOM series under MR/pseudo_muMAP/.

MR/pseudo_muMAP/

The final pseudoCT is written here as a DICOM series for downstream PET/MR use.

att_map.nii

The final pseudoCT attenuation map in NIfTI format.

Fusion_MR_Pseudo_CT_validation.tiff

QC image used to inspect MPRAGE/pseudoCT coregistration.

pseudo_CT_local-current_*.log

Detailed processing log for the subject.

pseudo_CT_profile_summary.txt

Concise provenance record of the selected profile, important settings, and MATLAB environment.

Pseudo_CT_AC_Version.txt

Records the pseudoCT software version and associated release history.

Profile provenance

The profile summary is useful when checking or reporting exactly how a subject was processed.

During processing, intermediate files are staged under MR_PET/tmp/. On a successful run this temporary directory is cleaned up. If processing is interrupted, intermediate files are retained.

Quality control

Every generated pseudoCT should be visually inspected before it is used for PET attenuation correction. QC has two parts: coregistration review and direct inspection of the final attenuation map.

1. Check MPRAGE / pseudoCT coregistration

Open Fusion_MR_Pseudo_CT_validation.tiff from MR_PET. Inspect the overlaid MPRAGE and pseudoCT in all displayed orientations.

Look for:

  • consistent alignment of the pseudoCT with the MPRAGE anatomy;
  • agreement of the skull and brain contours;
  • reasonable alignment around the nose, sinuses, and posterior head;
  • no gross atlas-registration mismatch;
  • no missing, displaced, or obviously distorted skull regions;
  • no obvious failure related to poor positioning of the brain within the field of view.

2. Inspect the final DICOM pseudoCT

Open the DICOM series in MR/pseudo_muMAP/ using a proper DICOM image viewer and scroll through the entire volume. Do not rely only on the TIFF fusion image.

Inspect for unexpected attenuation values or artifacts inside and outside the head. A known failure mode is background noise in the MPRAGE being segmented and classified as soft tissue instead of air, producing spurious tissue-like attenuation in the background.

If background tissue-like artifacts are present

Do not use the pseudoCT without further review. Clean the MPRAGE background, save the cleaned image as a NIfTI file under MR_PET, and rerun pseudoCT. A dedicated background-cleanup tool is planned for release.

Troubleshooting

Problem What to check
run_pseudo_CT is not found Confirm that the actual pseudoCT_standalone-latest or numbered-release directory was added to the MATLAB path.
The UMAP field does not auto-populate Confirm that the subject contains an MR/UMAP folder with the correct UMAP acquisition and that the MPRAGE comes from the expected subject directory.
Processing was interrupted Intermediate files may remain under MR_PET. Rerun pseudoCT; processing restarts from the beginning and overwrites existing processing files as needed.
MPRAGE and pseudoCT are visibly misregistered Do not use the result. Verify the selected MPRAGE, inspect positioning, leave the automatic correction options enabled, and rerun. Review the log if the problem persists.
Soft-tissue-like attenuation appears in the background Inspect the MPRAGE for background noise. Clean the background, place the resulting NIfTI in MR_PET, and rerun pseudoCT.
Launchpad does not run The legacy Launchpad workflow is currently unavailable and will soon be discontinued/decommissioned. Its source and profile are retained only for transitional/reference purposes. Use Local MATLAB for routine processing; do not treat Launchpad as a recommended usable remote.
MLSC does not submit MLSC uses the same username/password SSH login as the historical Launchpad workflow. Confirm the login was accepted (mlsc.nmr.mgh.harvard.edu reachable on port 22, correct Martinos credentials). Cancelling the login dialog or the account-selection dialog stops before submission, and a user with zero available Slurm accounts cannot submit. Check the run log for the exact stage message. Crypto/transport compatibility is proven by the manual login-host diagnostic; the live readiness checks A–D above are what remain open. Until MLSC passes those checks, use Local MATLAB for routine processing. Do not weaken authentication handling or switch SSH transports silently; retain the failure detail for support.
MLSC finishes without an attenuation map A scheduler COMPLETED state is not sufficient. Confirm that node-local att_map.nii was non-empty and that the shared MR_PET/tmp/att_map.nii copy-back is present and non-empty. Local finalization is not started when this verification fails; retain the log and temporary files for diagnosis.
When asking for help

Keep the run log, pseudo_CT_profile_summary.txt, QC TIFF, and software version available. These files usually provide the most useful first-pass information for diagnosing a failed or suspicious run.
